# BizArc Codebase Remediation & Implementation TODO List

This document is the verbatim checklist of all reviewer flags across the codebase, organized into actionable tasks.

## 1. Mocks, Fake Executions & Silent Fallbacks

- [x] **1.1 ViemWalletAdapter.executeContract fakes transaction confirmation on failure**
  - **Location:** `src/foundation/wallets/viemWalletAdapter.ts`
  - If `targetContract` is `0x4444...4444` or `0x5555...5555`, or if an RPC call fails with `"gas required exceeds allowance"` or `"execution reverted"`, the catch block swallows the error and returns `{ status: "CONFIRMED", txHash: "0x..." }` fabricated from `Date.now()`.
  - **Action:** Remove fabricated confirmation. Propagate real revert/gas errors or return explicit `{ status: "FAILED", error }`. Gate any simulation strictly behind `process.env.NODE_ENV === "test" && process.env.ENABLE_MOCKS === "true"` with loud logs.

- [x] **1.2 LedgerWitnessService.reconcileTransactionReceipt fakes blockchain receipts**
  - **Location:** `src/services/ledgerWitnessService.ts`
  - When `getTransactionReceipt` fails, if `txHash` starts with `0x0000` (which matches the `Date.now().toString(16).padStart(64, "0")` hashes generated by `ViemWalletAdapter`, `TokenSwapService`, and `FiatPayoutRail`) and `!process.env.CI`, it returns a simulated `{ status: "success", blockNumber: 1234567n }` receipt without verifying anything on-chain.
  - **Action:** Delete fake receipt shortcut. Query Arc L1 RPC directly and fail honestly if receipt is missing or unmined.

- [x] **1.3 FiatPayoutRail does not call any banking/Circle Mint API**
  - **Location:** `src/payments/rails/fiatPayoutRail.ts`
  - Generates synthetic payout references (`CIR-WIRE-...`, `CIR-ACH-...`, `CIR-CARD-...`, `IMAD...`) via `crypto.createHash` and `Date.now()`, writes a DB row, and transfers USDC to `0x0000...0000` (or fabricates a `0x${Date.now()}` hash if that fails).
  - If a vendor exists in `vendor_master_registry` without bank details, it invents fake bank details (`US12345678901234`, `021000021`, `"Commercial Settlement Clearing Bank"`) and stores them as `is_verified: true`.
  - **Action:** Integrate real Circle Mint Payouts API (`POST /v1/payouts`), remove `0x0000...0000` transfer dumps, remove fake bank account creation, and reject unverified bank details.

- [x] **1.4 AccountFundingService & FiatFundingService use hardcoded coordinates & fake hashes**
  - **Location:** `src/services/accountFundingService.ts`, `src/services/fiatFundingService.ts`
  - Hardcodes static BNY Mellon/SEPA coordinates (`routingNumber: "021000018"`, `accountNumber: "8900481239"`, `iban: "LU1200000000000000000"`).
  - Constructs synthetic `https://checkout.circle.com/onramp?...` URLs without calling Circle.
  - `reconcileDeposit` / `recordFiatDeposit` fabricate a SHA-256 `txHash` and directly bump numbers in `dynamic_safe_to_invest` with no real minting/settlement.
  - **Action:** Replace hardcoded bank coordinates with dynamic tenant bank records. Call Circle APIs for real checkout sessions. Require genuine onchain or webhook mint verification before crediting ledger.

- [x] **1.5 TokenSwapService falls back to hardcoded prices & address(0) transfers**
  - **Location:** `src/services/tokenSwapService.ts`
  - If `SwapKit.estimateSwap` throws, it silently uses hardcoded rates (`ETH = 2650`, `SOL = 145`, `EUR = 1.08`, `stables = 0.9995`).
  - If `SwapKit.swap` fails, it falls back to `USDC.transfer(0x0000...0000, amount)` or a `Date.now()` hex hash.
  - **Action:** Remove hardcoded price fallbacks; throw `PricingUnavailableError`. Remove `0x0000...0000` transfer and fake hash fallbacks on swap failure.

- [x] **1.6 GatewayX402Rail doesn't execute real x402 payments**
  - **Location:** `src/payments/rails/gatewayX402Rail.ts`
  - Unless a pre-signed `x402Payment` header is passed in, it only probes the URL, creates a synthetic `gw_nano_<hash>` reference and SHA-256 `txHash` (and on localhost / test URLs, swallows network errors completely).
  - **Action:** Implement complete client-side HTTP 402 challenge-response flow (read `WWW-Authenticate`, generate Gateway payment payload, sign, and resend).

- [x] **1.7 ModularSessionKeyRail falls back to standard EOA transfers**
  - **Location:** `src/payments/rails/modularSessionKeyRail.ts`
  - Unless `BIZARC_BUNDLER_URL` and a pre-built `userOperation` are provided, it ignores ERC-4337/ERC-6900 session keys and just calls `USDC.transfer` from the global `ArcTransactionExecutor` EOA—and auto-creates missing session keys on the fly in `SessionKeyRepo`.
  - **Action:** Enforce real session key signature validation and bundler dispatch; remove the global EOA transfer fallback and auto-creation of unauthorized session keys.

- [x] **1.8 Erc3009AuthorizationRail self-signs & swallows on-chain errors**
  - **Location:** `src/payments/rails/erc3009AuthorizationRail.ts`
  - If no `v, r, s` signature is supplied, it signs `ReceiveWithAuthorization` using the executor/admin key itself. If the on-chain call fails, the catch block fabricates a SHA-256 `txHash` and still marks `status: "EXECUTED"` and records the nonce.
  - **Action:** Reject authorizations missing debtor signatures. Throw real errors on contract failure and do not mark failed calls as `EXECUTED`.

- [x] **1.9 ErpReconciliationService fakes ERP sync success on failure**
  - **Location:** `src/services/erpReconciliationService.ts`
  - Both `erpNext.postPaymentEntry` and `odoo.registerPayment` are wrapped in try/catch blocks that return `{ success: true, docName: "PE-STAGED-..." }` or a random `paymentId` on failure, falsely marking `erp_sync_state` as `SYNCED`.
  - **Action:** Return `{ success: false, error }` and record `FAILED_RETRY_PENDING` in `erp_sync_state` upon sync failure.

- [x] **1.10 AutonomousSchedulerService.executeDueLiabilities hardcodes balances**
  - **Location:** `src/services/autonomousSchedulerService.ts`
  - Sets `balances[acc.account_id] = 50000.0` for every account instead of reading real balances.
  - **Action:** Query real operating balances from `DynamicRecordsService` or `TreasuryAccountsRepo`.

- [x] **1.11 ToolRegistry hardcoded fallbacks**
  - **Location:** `src/tools/toolRegistry.ts`
  - `execute_disbursal` defaults missing inputs to `"vendor_cloud_aws"`, `"Amazon Web Services"`, `"PO_DEFAULT"`, `"0xgrn_verified"`, and hardcoded `"0x5555...5555"`.
  - `post_document_linked_gl` returns hardcoded `odooSync: { status: "DISPATCHED" }` and `erpNextSync: { status: "DISPATCHED" }` objects without calling Odoo or ERPNext.
  - **Action:** Require explicit vendor, PO, and GRN parameters; fail if missing. Call actual `ErpReconciliationService` for GL syncing.

- [x] **1.12 DeterministicSimulatedLlmEngine default & bypass**
  - **Location:** `src/llm/llmEngine.ts`
  - `createLlmEngine()` checks `process.env.OPENAI_API_KEY` to decide between real LLM and "simulation"—ignoring `OPENROUTER_API_KEY` and `LLM_API_KEY` unless `LLM_PROVIDER` is explicitly set.
  - The simulated engine directly calls `ClearanceCodeRepo.issueCode(...)` inside its response generator, bypassing `PolicyComplianceAgent`.
  - **Action:** Recognize `OPENROUTER_API_KEY`, `LLM_API_KEY`, and `GEMINI_API_KEY`. Prevent simulated engine from issuing clearance codes directly without policy verification.

- [x] **1.13 Circle Wallet execution returns UUID as txHash**
  - **Location:** `src/foundation/wallets/arcTransactionExecutor.ts`
  - Immediately returns `{ status: "CONFIRMED", txHash: circleResult.transactionId }` (a Circle UUID, not an EVM hash) without polling Circle for confirmation, and silently falls back to `ViemWalletAdapter` on error.
  - **Action:** Poll Circle's transaction status endpoint until confirmed onchain and retrieve the real EVM transaction hash.

- [x] **1.14 Frontend is 100% fixture-driven**
  - **Location:** `frontend/src/context/TreasuryContext.tsx`, `frontend/src/fixtures.ts`
  - Never calls `treasuryApi.ts` or opens `/api/events` SSE; all state is local React state seeded from `fixtures.ts`.
  - `OnboardingView.tsx` "Activate" button only runs a `setTimeout(..., 800)`.
  - `FundModal.tsx` "Simulate Inbound Deposit" only sets a local boolean flag and closes without updating balances.
  - `SprCard` in `domain.tsx` attaches a hardcoded string `"0x7a89b1c2d3e4f506...AmaraLedgerEIP712Approved"` instead of calling a Web3 wallet.
  - **Action:** Fully connect `TreasuryContext.tsx` to `treasuryApi.ts` and SSE `/api/events`. Wire Onboarding activation to `POST /api/onboarding/activate`. Wire funding modal to backend. Connect real Web3 wallet signing.

## 2. Wiring Breaks, Runtime Bugs & Contract Mismatches

- [x] **2.1 Double-crediting bug on Circle Mint webhook**
  - **Location:** `src/ingress/systemHttpServer.ts`
  - `POST /api/webhooks/circle` and `/api/webhooks/circle-mint` call both `this.fiatFundingService.recordFiatDeposit(...)` and `this.accountFundingService.reconcileDeposit(...)` for the exact same deposit—appending two Master Journal entries, two audit logs, and crediting the account balance twice.
  - **Action:** Consolidate into a single idempotent deposit handler.

- [x] **2.2 Broken SQL query in PolicyComplianceLlmAgent.processHumanDecision**
  - **Location:** `src/agents/policyComplianceLlmAgent.ts`
  - Runs `UPDATE account_liabilities SET is_active = false, notes = ... WHERE liability_id = $2`. Neither `is_active` nor `notes` exists in `database/schema.sql` for `account_liabilities`, so cancelling a liability-linked SPRS through this method throws a SQL column error.
  - **Action:** Update SQL to use existing schema columns (`status = 'CANCELLED'`, metadata JSONB, or audit trail).

- [x] **2.3 Fake DB transaction in OnboardingWizardService.activateOrganization**
  - **Location:** `src/services/onboardingWizardService.ts`
  - Opens a client with `BEGIN` / `COMMIT` / `ROLLBACK`, but every repo call inside (`TenantRepo`, `TreasuryAccountsRepo`, `VendorMasterRepo`, `LiabilityRepo`, `MasterJournalRepo`, `AuditLogRepo`, `WizardSessionRepo`) uses `DbClient.query()` on separate pool connections—so rollback does not roll back any of the writes.
  - **Action:** Pass the transaction client through to each repository method.

- [x] **2.4 Double/triple execution inside State Machines**
  - **Location:** `src/orchestration/stateMachines/`
  - **LiabilityDisbursalStateMachine.executeDueLiability:** Runs `predictiveRefunder + disbursalRouter.qualifyDisbursalRoute` $\rightarrow$ runs `routerAgent.stageAndDisburseLiability` (an LLM loop that executes payment & GL tools) $\rightarrow$ runs `complianceAgent.evaluateIntent` $\rightarrow$ runs `new DisbursalRouter().executeLiabilityDisbursal` $\rightarrow$ runs `witnessAgent.recordSettlementVoucher`. A single due bill can trigger multiple payments/GL vouchers.
  - **YieldRebalancingStateMachine.handleBalanceMutation:** Runs `sentinelAgent.rebalanceAccountLiquidity` (executes sweeps/recalls via tools) AND THEN immediately calls `sentinelService.onBalanceMutation` (evaluates and sweeps/recalls again).
  - **LiabilityDiscoveryStateMachine.ingestAndProcessInvoice:** Runs `radarAgent.ingestAndVerifyInvoice` (which stages a liability via `add_account_liability`) AND THEN calls `LiabilityRepo.createLiability` again, creating duplicate liabilities.
  - **Action:** Refactor state machines to ensure single-responsibility execution and prevent duplicate trigger cascades.

- [x] **2.5 Dual, disconnected Payment & Onboarding Systems**
  - Two separate disbursal routers (`DisbursalRouterService` in `src/services/disbursalRouterService.ts` vs `DisbursalRouter` $\rightarrow$ `UniversalPaymentRouter`) with separate in-memory idempotency sets (`executedIdempotencyKeys` vs `localExecutedKeys`).
  - Two separate onboarding flows (`EnterpriseOnboardingService` vs `OnboardingWizardService`).
  - `SystemHttpServer` calls `VendorMasterRepo` / `LiabilityManagementService` directly on `/api/vendors` and `/api/liabilities`, bypassing the SPRS gates implemented in `VendorLifecycleService` and `RecurringLiabilityService`.
  - **Action:** Unify into one authoritative Disbursal Router and one Onboarding pipeline. Route all liability/vendor mutations through proper lifecycle and SPRS gate services.

- [x] **2.6 In-memory-only state that resets on restart**
  - `ProductionReadinessService` keeps `circuitBreakerTriggered`, `emergencyReason`, `activeVaultOverride`, and `isVaultAllowlisted` in static in-memory fields (never in PostgreSQL).
  - `DisbursalRouterService.executedIdempotencyKeys`, `DisbursalVaultRail.localExecutedKeys`, `AccountLockManager.locks`, `PolicyLoader.dynamicProfile`, `SystemHttpServer.discoveryJobs`, and `siweNonces` are all in-memory only.
  - **Action:** Persist governance state, idempotency keys, advisory locks, dynamic policies, and SIWE nonces to PostgreSQL.

- [x] **2.7 Frontend TypeScript & API Contract Mismatches**
  - **TreasuryContext.tsx omits required context fields:** `TreasuryContextType` declares `shortfalls`, `hasShortfalls`, `isLiveBackend`, `refreshData`, `runShortfallRebalance`, `createAccount`, and `updateAccountPolicy`, none of which are provided in `<TreasuryContext.Provider value={...}>`.
  - **TransferModal.tsx & AccountConfigModal.tsx don't match primitives.tsx or types.ts:** They pass `<option>` children to `Select`, omit render-props in `Field`, pass placeholder / wrong onChange signature to `UsdcInput`, use non-existent `Banner tone="positive"` and `Button variant="ghost"`, and reference non-existent `AccountDistribution` fields (`floorUsdc`, `safetyBufferMultiplier`, `payrollShieldActive`).
  - **Payload mismatches between treasuryApi.ts and SystemHttpServer.ts:**
    - `createFiatOnramp` sends `amountUsd`; server reads `amountUsdc` (undefined).
    - `reconcileFiatDeposit` sends `targetAccountId` & `wireReference`; server expects `accountId` & `depositReference`.
    - `fundAccount` sends `"CARD" | "ACH" | "CRYPTO"`; server expects `"FIAT_CARD_ONRAMP" | "FIAT_FEDWIRE" | ...`.
    - `transferFunds` sends `memo`; server reads `reason`.
    - **SSE event names mismatch:** `SystemHttpServer` emits `BALANCE_MUTATED`, `proposal:created`, `LIABILITY_MUTATED`; `treasuryApi.ts` listens for `balance:mutated`, `yield:swept`, `yield:recalled`, `deposit:confirmed`, `sprs:created`, `circuit_breaker:tripped`.
    - **Documented routes missing or renamed:** `docs/` lists `POST /api/invoices/inbound` (actual route is `/api/webhooks/ingest`) and `GET /api/ledger/entries` (actual route is `/api/journal`).
  - **Action:** Align all payload interfaces, prop types, enum values, SSE event types, and endpoint paths between frontend and backend.

- [x] **2.8 Multi-Tenancy & Authorization Leaks**
  - `SystemHttpServer` enforces `resolveTenantId` on some routes, but leaves `/api/operational-state`, `/api/treasury/distribution`, `/api/treasury/safe-to-invest` (when `accountId` omitted), `/api/liabilities/preflight-alerts`, `/api/liabilities/dispute`, `/api/webhooks/ingest`, `/api/events/balance-mutation`, `/api/disbursal/trigger-due`, `/api/payments/ad-hoc`, `/api/swaps/*`, `/api/funding/fiat/*`, `/api/disbursals/fiat`, `/api/onboarding/*`, and `/api/governance/*` unscoped by tenant or role.
  - `POST /api/sprs/:id/sign` signs on the server with `DEFAULT_ADMIN_PRIVATE_KEY` if no `privateKey` is passed, allowing any API user to self-sign as CFO.
  - `ToolRegistry.sweep_excess_liquidity` only checks `clearanceCode.startsWith("CLEAR-")` instead of validating/consuming it via `ClearanceCodeRepo`.
  - Most core services (`AccountIntelligenceService`, `TreasurySentinelService`, `DisbursalRouterService`, `PolicyComplianceLlmAgent`, `PredictiveRefunderService`) still read `PolicyLoader.getActiveProfile()` (global singleton) rather than `TenantPolicyManager.getActiveProfile(companyId)`.
  - `DisbursalVaultRail` and `FiatPayoutRail` hardcode a $500 human gate threshold instead of reading tenant policy.
  - `DisbursalRouterService.qualifyDisbursalRoute` catches `DataFeedError` and silently substitutes `investedUsyc: "0.000000"`, and `AccountIntelligenceService.getOnchainUsdcBalance` silently returns 0 on error (contradicting Rule 5).
  - **Action:** Scope all endpoints with tenant authentication; require client-side EIP-712 signatures; validate and consume clearance codes; pass `companyId` to tenant policy managers; enforce tenant policy spending gates; propagate onchain balance errors strictly.

- [x] **2.9 Math Q&A / Policy Mapping Mismatch (MathRulesQAEngine vs TenantPolicyManager)**
  - `MathRulesQAEngine` defines two overlapping sets of questions (15 uppercase `GM_*`/`AM_*`/`LM_*`/`IM_*` and 11 lowercase `gen_*`/`acc_*`/`liab_*`/`inv_*`), and `TenantPolicyManager` looks up parameter names (`investHysteresisBandUsdc`, `recallHysteresisBandUsdc`, `taxHoldbackPercentage`) that `MathRulesQAEngine` never emits (`hysteresis_band_usdc` vs `investHysteresisBandUsdc`).
  - **Action:** Unify into a single question ID and derived parameter mapping dictionary shared across both engines.
